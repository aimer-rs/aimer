# 26.0.0-dev.2

Changes since `26.0.0-dev.1`.

## New Features

### Shortcuts

- **Local shortcuts** with the `Shortcuts` widget (`aimer::shortcut`). Chords such as `"CmdOrCtrl+K"` or `F5` run an action while focus is inside the subtree, the innermost scope wins, and `.window(true)` makes a scope active wherever focus is. Nothing is checked until the first scope exists, so apps that do not use shortcuts pay nothing.
- **Application menu** with `aimer::shortcut::menu`. Describe the menus once with `AppMenu`: macOS builds a native menu with the shortcut shown beside each item, and every other platform runs the same chords as window-wide shortcuts.
- **Global shortcuts** with `GlobalShortcut`, which fire while the app is in the background: Carbon hot keys on macOS, `RegisterHotKey` on Windows and X11 key grabs on Linux. Wayland, iOS, Android and web report `Unsupported`.
    - Only the macOS backend has been run. The Windows and Linux backends are compile-checked only.
- The **Shortcuts** page in the Jaime showcase (and `cargo run -p aimer --example shortcuts`) shows all three kinds and logs what fires.

### Windows

- **Frosted windows** with the `WindowBackdrop` widget (`aimer::WindowBackdrop`, `aimer::WindowMaterial`). Wrap a window's content in it and the system blurs the desktop and the windows behind it through everything the content draws with some transparency, like a Finder sidebar. The blur is drawn by the system, and the window is restored when the widget leaves the tree. See `cargo run -p aimer --example window_backdrop`.
    - `WindowMaterial::Glass` and `WindowMaterial::ClearGlass` give the refractive Liquid Glass look of macOS 26 and later through an `NSGlassEffectView`, falling back to the sidebar blur on older systems. Jaime's sidebar uses `Glass`.
    - macOS uses an `NSVisualEffectView` and has been run. Windows asks DWM for a Mica or Acrylic backdrop and is compile-checked only; the Windows renderer's swap chain ignores alpha, so the backdrop may not show through there yet. Other platforms ignore the widget.

### Media

- **Audio** playback on macOS and iOS, with Android, Windows, Linux and web backends. Remote audio streams while it downloads, and the seek bar is draggable.
- **Video** playback with zero-copy frames on macOS and iOS, plus backends for Windows (MediaPlayer frames as shared D3D textures) and web (copied from an `HTMLVideoElement`).
    - Linux and Android not have been finished yet
- A standard **video player** widget with captions, chapters and fullscreen.
- **GIF** support in assets.
- **Lottie** animation support.
- **Haptic feedback** for macOS and Android.
- **System notifications** with `aimer::notification` (`aimer_notification`). Show, replace, schedule and close a notification with a title, subtitle, body, sound and buttons, ask for the permission, and hear clicks, buttons and dismissals on the event loop through `notification::install`. macOS and iOS use `UNUserNotificationCenter`, Linux the freedesktop D-Bus service, Windows a notification-area balloon and Android `NotificationManager`. Push is client side: `Notifier::register_push` asks for a token and launcher glue reports it through `notification::push`. In-window messages remain the toasts in `aimer::feedback`.
- **Live activities** with `aimer::live_activity` (`aimer_live_activity`, feature `live-activity`). `LiveActivities::show` starts or updates, and `end` ends, one glanceable activity described by a title, body, short status, progress, milestones, an icon and optional custom state. Android posts a Live Update (`Notification.ProgressStyle` with a promoted-ongoing request on Android 16, an ongoing progress notification before). iOS 16.2+ drives ActivityKit through a Swift bridge the app ships, found with `dlsym` so an app without it still links, plus a live-activity-only widget extension in SwiftUI; the custom state is readable by a custom SwiftUI view and ignored elsewhere. macOS (whose SDK marks ActivityKit unavailable), Windows and Linux report `Unsupported` unless the app opts in to a tray icon with `LiveActivitiesBuilder::tray_icon`.
    - Only the portable model, the JSON contract with Swift and the tray bookkeeping have run. The Android backend is compile-checked, and the Swift files are type-checked against the iOS SDK; none of them has run on a device.
    - `LiveActivity::countdown` gives an activity a deadline the system ticks by itself, so the clock on the Dynamic Island, the lock screen and the Android chip keeps moving while the app is suspended in the background (`Text(timerInterval:)` and `ProgressView(timerInterval:)` on iOS, a count-down chronometer on Android). Before, text pushed from the app froze as soon as the app went away. Projects whose widget Swift was generated earlier keep their copy: take the new `AimerLiveActivityAttributes.swift` and `AimerLiveActivityWidget.swift` from `native/live_activity/swift`.
    - `UIKitWidget` describes views for the Dynamic Island and the lock screen as data, and `LiveActivity::view(Region, widget)` fills one slot of the island or the lock screen with it. It is deliberately not an Aimer `Widget`, so it cannot be placed in an Aimer tree. The built-in `Label`, `Symbol`, `Bar`, `Clock`, `Row`, `Column` and `Gap` are drawn by a generic SwiftUI interpreter in the widget extension, and the clock and bar follow the system-ticked countdown. Android and the tray ignore views. Projects whose widget Swift was generated earlier must take the new `AimerLiveActivityAttributes.swift` and `AimerLiveActivityWidget.swift` from `native/live_activity/swift`.
    - The Jaime showcase has a **Live activity timer** page: set a timeout with the plus and minus buttons, start it, and the time left is mirrored in a live activity (a Venus task ticks once a second, so it works on every platform).

### Stateful widgets

The stateful widget API was reworked; see **Breaking** under Changes for the migration.

- **A state no longer stores its own updater.** `build` receives a `StateView`, which derefs to the state, so fields are read directly (`this.count`), and `this.updater()` is the `Copy`, `'static` handle that callbacks use. The "add this line to `init_state`" panic for a forgotten `self.updater = updater` is gone with the field.
- **The state type can be private.** It is named by `#[state(MyState)]` on the widget and only inside the body of the derived `to_element`, never in a signature, so it no longer has to be `pub` (it used to fail with E0446).
- **`init_state(&mut self)` is optional and plain.** It runs once, before the first build, and mutates the state directly.
- **`on_mount(&mut self, updater)`** runs right after `init_state` and hands the state its `StateUpdater`, for registering something that has to reach back into it later: a back or link handler, a subscription, a repaint callback.
- **`StateUpdater::mounted()` and `StateView::mounted()`** tell a callback whether its widget is still in the tree. Use it before touching the state from a timer, a request or a task that can outlive the element. It is the same quiet check as `has_state()`.

    ```rust
    let updater = this.updater();
    spawn(async move {
        let data = fetch().await;
        if updater.mounted() {
            updater.set_state(move |state| state.data = Some(data));
        }
    });
    ```

- **Compile-time protection.** Capturing `this` in a `'static` closure does not compile, so a handler cannot read a stale reference. A handler that has to read the state when it runs takes `this.updater()` and uses `read` or `try_read`.
- For tests: `widget.create_state::<MyState>()`, `state.build_element(&ctx)` and `StateView::detached` (all `#[doc(hidden)]`) build a state without mounting it.

### Venus

- Added `spawn`: spawns a `!Send` future as a microtask that runs before the next build phase.
- Added `join!`: polls several futures together inside the awaiting task and returns all outputs as a tuple. Nothing is spawned or boxed per future.
- Added `join_all`: does the same for a collection of futures and returns the results in input order, not finishing order.
- Added `JoinHandle`: an owned handle to a spawned task. Dropping it cancels the task.
- Added `oneshot`, `mpsc`, `watch`: single-threaded channels for passing values between tasks.
- Added `Notify`, `Semaphore`: wake-up and permit primitives for coordinating tasks.
- Added `OnceCell`, `Shared`: compute a value once, or share one future's result between many awaiters.
- Added `Stream`, `StreamExt`: a minimal stream trait with combinators.
- Added `Latest`: keeps only the newest result of overlapping async work.
- Added `retry`, `retry_when`, `Backoff`: retry a failing future with a backoff policy.
- Added `FutureExt`: extension methods on futures.
- Added `next_frame`, `on_idle`, `run_in_phase`: hop a task to a chosen frame phase.
- Added `run_until`, `run_until_stalled`: drive Venus without an event loop, for tests and tools.

### Remote control and capture

- Added `aimer_prendre`: sends synthetic input to a running **debug** app, so a tool or an agent can drive it. A release build never starts the server. It is two Cargo features, `client` (no dependencies) and `host`.
    - Every event a person or the system can cause from outside the process has a command: pointer, touch, scroll, pinch, rotate, pan, keys, text and IME preedit, back, links, menu shortcuts and file drops.
    - The protocol is one text line per command over TCP, guarded by a random per-run token. `AIMER_PRENDRE=1` starts the server; `Config::bind` and `AIMER_PRENDRE_BIND` choose the address, for reaching an app on a phone.
    - The mouse **glides** along a curved, eased path to its targets instead of jumping, and a command sent mid-glide retargets it. Clicks, drags and scrolls glide too; a scroll takes an optional position, and without one scrolls where the mouse is.
    - `scroll` is a smooth **trackpad-style swipe**, which the framework treats as a trackpad and not as a wheel.
    - `typing` types one keystroke at a time at an uneven, human pace. `text` is still one instant edit.
    - `down` and `up` take no coordinates to mean "where the mouse is now", and `actions::click` takes an optional point.
    - `screenshot` returns a picture of the window as a PNG or JPEG, at the window's logical size by default so a point in it is a point that can be clicked.
- Added `aimer_capture`, in `content/`: `screenshot()` takes a picture of the app's window and `Image` encodes, crops and scales it. The `Capture` widget and its `CaptureHandle` pick out the part of the window a child covers. It is behind the umbrella crate's `capture` feature. Only the Metal renderer can copy a frame so far; the others answer `Unsupported` at once.
- Added `aimer_platform::capture` and `aimer_platform::attachment`: a request slot for a picture of the window, and the list of who is connected to the app. The list tells the tool that launched the app (`Role::Launcher`) from an agent that is controlling it (`Role::Agent`); a client that does not say is an agent.
- The debug overlay shows when an agent is controlling the app: a pill badge with the `square-mouse-pointer` icon in the top-right corner, and a cursor, a finger ring and a press ripple where each injected pointer is, so a screenshot shows what the agent did. They fade in when an agent connects and out when the last one leaves. The cursor sways slightly when it rests. Debug builds only.

### Migrating stateful widgets

A counter, before and after:

```rust
// Before
#[derive(StatefulWidget)]
pub struct Counter {
    pub start: i32,
}

pub struct CounterState {        // had to be `pub`: `type State` named it
    updater: StateUpdater<Self>, // every state stored its own updater...
    count: i32,
}

impl StatefulWidget for Counter {
    type State = CounterState;

    fn create_state(self) -> CounterState {
        CounterState { updater: StateUpdater::empty(), count: self.start }
    }
}

impl State<Counter> for CounterState {
    fn init_state(&mut self, updater: StateUpdater<Self>) {
        self.updater = updater;  // ...and forgetting this line panicked on first use
    }

    fn build(&self, _ctx: &BuildContext) -> impl Widget {
        let updater = self.updater;
        let _increment = move || updater.set_state(|state| state.count += 1);
        Text::new(format!("Count: {}", self.count))
    }
}
```

```rust
// After
#[derive(StatefulWidget)]
#[state(CounterState)]
pub struct Counter {
    pub start: i32,
}

struct CounterState {            // private is fine now, and there is no updater field
    count: i32,
}

impl State<Counter> for CounterState {
    fn create(widget: Counter) -> Self {
        Self { count: widget.start }
    }

    fn build(this: &StateView<Self>, _ctx: &BuildContext) -> impl Widget {
        let updater = this.updater();
        let _increment = move || updater.set_state(|state| state.count += 1);
        Text::new(format!("Count: {}", this.count))   // fields are read through `this`
    }
}
```

Steps:

1. Add `#[state(YourState)]` to the widget, and delete the `impl StatefulWidget` block. Its `create_state(self)` body becomes `State::create(widget: YourWidget) -> Self`, with `self.` becoming `widget.`.
2. Delete the `updater` field, its initializer and the `init_state` line that stored it. If `init_state` has nothing else in it, delete it.
3. Change `fn build(&self, ctx)` to `fn build(this: &StateView<Self>, ctx)`. `self.field` becomes `this.field`, and `self.updater` becomes `this.updater()`.
4. If a state's own `&self` helper methods read `self.updater`, pass `this.updater()` to them as a parameter. If that is not practical, keep an `updater` field and set it in `on_mount`.

An `init_state` that hands the updater to something that outlives the call becomes `on_mount`:

```rust
// Before
fn init_state(&mut self, updater: StateUpdater<Self>) {
    self.back_guard = Some(back::register(NavigatorBack { updater }));
}

// After
fn on_mount(&mut self, updater: StateUpdater<Self>) {
    self.back_guard = Some(back::register(NavigatorBack { updater }));
}
```

`on_mount` runs after `init_state`, so anything it relies on that `init_state` sets up is in place. Prefer `try_set_state` and `try_read` in what you register: it can run after the element is gone.

A widget with a hand-written `Widget` impl names its state in the call, which is also what lets the state stay private:

```rust
// Before
StatefulElement::from_widget(self, ctx, "Page", None)

// After
StatefulElement::from_widget::<Self, PageState>(self, ctx, "Page", None)
```

Tests that built a state directly:

```rust
// Before
let state = widget.create_state();
let element = state.build(&ctx).to_element(&ctx);

// After
let state = widget.create_state::<CounterState>();
let element = state.build_element(&ctx);
```

A test that grabbed the updater in `init_state` to drive the state from outside publishes it from `build` instead, with `this.updater()`.
